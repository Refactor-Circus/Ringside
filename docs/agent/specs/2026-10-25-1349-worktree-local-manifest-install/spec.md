# Install job worktree dependencies from composer.local.json

Ticket: [T-001](../../tickets/T-001.md)

## Goal

A single package's per-job worktree ends up with the same dependencies as its main checkout (including the `composer.local.json` path repositories), set up by one allowed Ringside command, so the factory gate (`vendor/bin/ringside check` and the rest) runs inside it.

## Acceptance criteria

1. `vendor/bin/ringside worktrees <spec>` in a single package (no `workspace.packages`) with `build.worktree.mode: per-job` creates the worktree at the job's `job.worktree` path on branch `ring-master/<spec>` (new branch from `host.base`, or the existing branch) and prints exactly `<path> on <branch>` (with `--setup`, followed by `, set up with <description>`). It no longer fails with "No workspace.packages…".
2. Run again when the worktree folder already exists on branch `ring-master/<spec>`, it reuses it (no `git worktree add`, exit 0). When the existing worktree is on any other branch (or a detached HEAD), it exits 1 with a message naming the actual branch and the expected `ring-master/<spec>`, and changes nothing (D-007).
3. With `--setup` and `build.worktree.setup: auto` (the new default) and a `composer.local.json` at the package root, the command copies `composer.local.json` into the worktree, and `composer.local.lock` too when present, each file only when it is absent in the worktree. It then runs `composer install --no-interaction` in the worktree with `COMPOSER=composer.local.json` in its environment.
4. Rerun with `--setup` when the worktree already holds its own `composer.local.json` and/or `composer.local.lock` (different contents from the package's): both are left untouched, and the install still runs.
5. With `--setup`, `auto` and no `composer.local.json`, it runs `composer install --no-interaction` in the worktree with `COMPOSER` unset or empty (whatever the caller's environment holds), and copies nothing.
6. With `--setup` and an explicit `build.worktree.setup` command string (anything but `auto`), it runs that command in the worktree as is, without copying manifests.
7. It never runs a package's `composer local:install` for a single-package job, even when the script exists.
8. When the setup command exits non-zero, the command prints `<error>` followed by the command and its output, which includes the child's stderr, and exits 1. A failed `git worktree add` also exits 1 with git's output.
9. When the worktree folder exists but is not a git worktree (no `.git`), `Worktree::prepare` throws a `RuntimeException` carrying git's output, and the command exits 1 with that output.
10. In a single package with `build.worktree.mode` other than `per-job`, the command exits 1 and prints a message containing `does not use a worktree`. With `--remove` in a single package, it exits 1 and prints a message containing `--remove is not supported`.
11. `Config` defaults `build.worktree.setup` to `auto`; an absent or empty value reads as `auto`, and a non-string value (list, map, number, boolean) fails loud with an error naming `build.worktree.setup` (D-008).
12. `Shell::run` has the signature `run(array $command, string $cwd, array $env = [], bool $withStderr = false)`. With no env argument the child inherits the parent environment, and with the flag off the returned output is stdout only, as before (git callers unchanged). With `$withStderr = true` the returned output also contains the child's stderr. The setup/install call is the only caller that turns it on. Both pipes are always drained, whatever the flag.
13. The factory workflow's per-job prepare prompt (single package) tells the agent to run `vendor/bin/ringside worktrees <spec> --setup` from the job root, return ready=true only if it exits 0, and on a non-zero exit return ready=false with the command output, without repairing manually or falling back to `git worktree add` or other commands. Workspace jobs keep their current prompt and `local:install` detection.
14. Workspace jobs (`workspace.packages` set) behave exactly as before for `worktrees`, `--setup` and `--remove`. Workspace setup keeps selecting its command per package (`composer local:install` when the script exists, else `composer install`) and ignores the `build.worktree.setup` default `auto`.

Tests (see Testing) cover criteria 1 to 14. `vendor/bin/pest` and the workflow tests (`tests/workflows/*.test.mjs`) pass.

## Design

- **`Shell::run(array $command, string $cwd, array $env = [], bool $withStderr = false)`** (D-005): when `$env` is non-empty, build the child environment with explicit key assignment (`$merged = getenv(); foreach ($env as $k => $v) { $merged[$k] = $v; }`, no array spread, which re-indexes numeric-looking names) and pass it as proc_open's `env_vars`; otherwise `null` (inherit) as today. Today's `run` reads stdout to EOF before stderr, so a child that fills the stderr pipe (composer install writes its progress and errors to stderr) blocks forever; the change drains both pipes without that deadlock (`stream_select`, or non-blocking reads), regardless of the flag. With `$withStderr` false the stderr text is discarded as today; with true it is appended to the returned output. Only `Worktree::setup` passes true.
- **`Worktree` (new, `src/Worktree.php`)**, the single-package counterpart of `Workspace::prepare`:
  - `prepare(Project $project, string $path, string $branch, string $base): string` — `$path` is used as is when absolute, else resolved against the project root (`Project::path` would mangle an absolute `build.worktree.path`). A branch or path starting with `-` is rejected with a `RuntimeException` before git runs (option injection from repo-controlled config). Reuse when `$path/.git` exists and `git branch --show-current` in it equals `$branch`; on any other branch (empty output for a detached HEAD) throw a `RuntimeException` naming the actual and expected branch, without touching the worktree (D-007). An existing folder that is not a worktree is not reused: git's own refusal is surfaced. Otherwise `git worktree add [<-b branch>] <path> <branch|base>` from the package root (same branch check as `Workspace::prepare`); throws `RuntimeException` with git's output on failure. Returns the path.
  - `setup(Project $project, string $path, string $setup): array{0: int, 1: string, 2: string}` — exit code, output (stderr included), and the description of what ran. `auto`: copy `composer.local.json` and `composer.local.lock` from the package root, each only when the file exists there and is absent in the worktree (D-006), then run `['composer', 'install', '--no-interaction']` with `['COMPOSER' => 'composer.local.json']` and `$withStderr = true`, or the plain install when there is no local manifest. Anything else: `preg_split` the trimmed string and run it, as workspace setup does. A failed `copy()` is reported like a failed install (exit 1, message naming the file), never ignored. The plain-install fallback must not inherit a `COMPOSER` variable from the caller's environment: it passes `['COMPOSER' => '']` (composer treats an empty value as unset), and a test proves it.
  - Copy and install behaviour is tested here (test-layers: behaviour once, where it lives).
- **`WorktreesCommand`**: when the workspace is not enabled, branch to the single-package path: check `build.worktree.mode === 'per-job'` (fail loud otherwise, message contains `does not use a worktree`), refuse `--remove` (message contains `--remove is not supported`), build the job, `Worktree::prepare` with `job.worktree` resolved against the project root, then `Worktree::setup` when `--setup`. Output: `<path> on <branch>[, set up with <description>]`. Description updated to cover single packages.
- **`Config`**: `build.worktree.setup` default `auto`; read through a new `Config::worktreeSetup(): string` with `auto` as the hard default when the key is absent, null or an empty string. Config has no fail-loud helper (`string()` silently casts scalars, so a number or boolean would become `"5"`/`"1"` and a list or map would become `''`), hence the dedicated method: it reads `get('build.worktree.setup')` and throws a `RuntimeException` naming `build.worktree.setup` for any non-string, non-null value (configuration standard, D-008). `WorktreesCommand` lets it surface as exit 1 with that message. `Worktree::setup` receives the already-validated string. Workspace setup does not read this key (`Workspace` picks its command per package), so the new default does not reach workspace jobs.
- **Factory workflow**: the per-job single-package branch of the prepare prompt calls `vendor/bin/ringside worktrees ${spec.id} --setup`, mirroring the workspace branch, and says what to do on failure (criterion 13). Its tests assert the new prompt.
- **Docs**: README (the `build.worktree` example at line 143 still shows `setup: composer install --no-interaction`) and CHANGELOG mention the `auto` default and single-package `worktrees`. The CHANGELOG states that the default changed for every consumer that never set `build.worktree.setup` (formerly plain `composer install`), and that with `auto` a package that has a `composer.local.json` now installs its job worktrees from that manifest, including its sibling path repositories.

## Testing

No real `composer install` runs in any test. `Shell` stays static (no injected runner); the seam is the process boundary.

- **Fake composer**: a test writes an executable `composer` script into a temp `bin/` dir that appends `cwd`, `$@` and `COMPOSER` (printed as `<unset>` when unset or empty) to a log file, prints a marker to stdout, and exits with a code taken from a `FAKE_COMPOSER_EXIT` env var (default 0). On a non-zero exit it also writes a distinct marker to stderr. The test prepends that dir to `PATH` with `putenv` and restores `PATH`, `COMPOSER` and `FAKE_COMPOSER_EXIT` in a `finally`/`afterEach`. `Shell::run` inherits or merges `getenv()`, so the fake is found in-process and in a `bin/ringside` subprocess. `skipOnWindows()`, as WorkspaceTest does. Assertions read the log: criterion 3 (args `install --no-interaction`, cwd is the worktree, `COMPOSER=composer.local.json`, manifest and lock contents equal the package's), 4 (pre-seed the worktree with different manifest and lock contents; they are unchanged after the run and the log shows the install ran), 5 (`COMPOSER` shows `<unset>` even when the test sets `COMPOSER=other` in the caller's env, and no file copied), 8 (exit 1 from `FAKE_COMPOSER_EXIT`; the stderr marker appears in the `Worktree::setup` output and in the command's printed output).
- **Criterion 6 and 7**: an explicit `setup` such as `touch setup-ran` runs in the worktree (marker file exists, no manifest copied). For 7, the fixture `composer.json` has a `local:install` script and the fake log must contain no `local:install` argument.
- **Git fixtures**: real temp repos, as WorkspaceTest does. Move `packageRepo()` from `tests/Feature/WorkspaceTest.php` to `tests/Pest.php` (it is a global helper; the new tests need it, and relying on another test file's load order is fragile). Criterion 1 covers both a new branch from `host.base` and an existing `ring-master/<spec>` branch (`git branch --show-current` and `git worktree list` in the worktree). Criterion 2 reruns and asserts the worktree list is unchanged and exit 0; a second case switches the existing worktree to another branch first and expects the `RuntimeException` (exit 1 at the command level) naming both branches, with the worktree still on the other branch. Criterion 9 creates a plain folder at the worktree path and expects the `RuntimeException` (and exit 1 at the command level). A branch or path starting with `-` is rejected without running git.
- **Layers** (test-layers): `Worktree::prepare`/`setup` behaviour in `tests/Feature/WorktreeTest.php` (needs git and the fake); `Shell::run` in `tests/Unit/ShellTest.php`: env merge, no leak into later calls, the fallback ignoring a caller's `COMPOSER`, `$withStderr` off (stdout only) and on (stderr included) with a `php -r` child, and a child writing more than 64 KB to stderr finishing, run under a deterministic bound (the child is wrapped with a fixed proc timeout, for example 10 seconds, and the test fails with a message naming the deadlock instead of hanging); `Config` default, empty (and null) reading `auto`, and each non-string kind (list, map, number, boolean) making `worktreeSetup()` throw with a message naming `build.worktree.setup`, in `tests/Unit/ConfigTest.php`; command wiring only (exit codes, exact output line, mode refusal text, `--remove` refusal text, workspace project still takes the workspace path and ignores `auto`) in `tests/Feature/WorktreesCommandTest.php`, driven through `bin/ringside worktrees` in a subprocess as `JobTest.php` does (the repo has no `CommandTester` tests), and asserting no install detail already proven in WorktreeTest. One command-level case sets `build.worktree.setup` to a list and expects exit 1 with the key named (D-008).
- **Workflow**: `tests/workflows/factory.test.mjs` adds a single-package case asserting the prepare prompt matches `/ringside worktrees <spec> --setup/`, contains the ready=false-on-failure and no-manual-repair wording, and no longer contains `git worktree add` or the configured `setup` string, next to the existing workspace case (line 147).

## Out of scope

- `worktrees --remove` for single packages (worktree cleanup stays with `build.worktree.cleanup`).
- Atrium's `bin/composer-local.php`; reinstalling the existing Atrium worktree (done when that job resumes).
- Rewriting relative path repositories in the copied manifest (siblings resolve the same from `../{package}--{spec}`).
- Custom `build.worktree.path` values that are not siblings of the package.
- Gitignoring the copied `composer.local.json`/`.lock`.
- Workspace jobs: workspace packages ignore `auto` and keep their current per-package setup selection.

## Risks and open questions

- A custom `build.worktree.path` that is not a sibling of the package would break `../Sibling` path repositories in the copied manifest; `auto` copies the manifest as is and leaves that to the user.
- Backward compat: a project that wrote `setup: composer install --no-interaction` explicitly (the README example) keeps that command and never gets the local manifest; the CHANGELOG says to delete the key to get `auto`. A project that never set the key moves from plain `composer install` to `auto` (see Docs).
- Copied `composer.local.json`/`.lock` are normally gitignored in the package; if not, the copy shows as untracked in the worktree. Not handled.
- `composer.local.lock` absent: composer resolves fresh in the worktree, which can pick different versions than the main checkout. Acceptable; matches the main checkout's own first install.
- Stale manifest (D-006): because copying skips files already present, a `composer.local.json` or lock changed in the main checkout after the worktree was first set up is not picked up on rerun. Accepted to protect in-job edits; delete the worktree's copy to refresh it.

## Addendum 2026-10-26 (D-012)

- `Worktree::prepare` passes `$withStderr = true` on its `git worktree add` call only, so criteria 8 and 9 surface git's refusal (written to stderr). Criterion 12's "the setup/install call is the only caller that turns it on" reads as "existing git callers stay unchanged": the setup/install call and the new `git worktree add` in `prepare` turn it on; every other `Shell::run` caller keeps stdout only. Design's "Only `Worktree::setup` passes true" reads the same way.
